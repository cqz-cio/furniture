# ERP 镜像下载与分层

## 当前可用方式

镜像仍由 GitHub CI 构建并发布到 GHCR。腾讯云上海仓库尚未创建，当前代码没有启用 TCR 推送、拉取或清理，不能把它当成已接通的下载源。

在 GitHub `test` Environment 中设置变量 `ERP_IMAGE_TRANSPORT`：

| 值 | 行为 |
| --- | --- |
| 不设置或 `ssh` | 默认：Actions 读取 GHCR 的固定摘要镜像，打包 OCI，经已配置的 SSH 通道导入测试服务器 |
| `ghcr` | 测试服务器直接从 GHCR 拉取固定摘要镜像；适合下载链路恢复后验证 |

拼写错误或填写 `tcr` 会明确失败，不会静默回退到另一条路径。生产环境保持原有 GHCR 直拉，本次不启用生产 SSH 中转。

SSH 传输完整保留镜像摘要，导入后核对 Linux/amd64 和 CI 提交标签；同一发行版已缓存时跳过下载和导入。它仅用于镜像准备，服务切换、数据库备份及迁移仍由原有 CD 状态机控制。下载失败不会自动开始切换。

Actions 下载单个 blob 短暂失败时最多重试一次；已有数据通过 HTTP Range 续传，拒绝范围不符或校验失败的数据。原有 300 秒归档总限时及服务器传输限时继续生效，认证失败不会反复重试。

## 新镜像布局

后端使用 Spring Boot 3.5 tools 模式生成四个镜像层：稳定依赖、启动器、快照依赖、应用代码。运行目录仍为 `/opt/yudao`，入口仍是 `java ... -jar app.jar ...`，但 `app.jar` 已不再包含全部依赖，依赖位于同目录 `lib/`。新镜像标记 `io.oakved.image.layout=spring-boot-tools-v1`。

CD 根据镜像标签兼容原有完整 JAR 和新的分层结构，并继续核对迁移 SQL 与发行清单的哈希。不得只把新 `app.jar` 复制到旧裸机服务中运行，必须携带整个 `lib/`，或直接运行完整镜像。

分层的主要收益是直接拉取时复用未变化的依赖层，不承诺首次下载明显缩小。当前 SSH 方案只跳过已完整缓存的同一发行版；传输不同发行版时仍发送完整 OCI 归档，尚未实现跨发行版的增量传输。

CI 构建 JAR 后执行 `deploy/erp/verify-image-layers.py`，校验依赖内容、迁移 SQL 和 Java 类路径，再进入镜像构建发布。检查不启动 ERP、不连接数据库。镜像构建本身仍由既有 CI 执行。

## 上海仓库的后续接入条件

先在腾讯云选择上海地域并确认版本和费用。需要仓库域名、命名空间、CI 推送凭证及服务器只读拉取凭证；凭证存放 GitHub Secrets/服务器受限配置，勿写入 Git。

仓库实际可用后再完成：

1. CI 将同一构建产物同步到上海仓库，核对同步后摘要；保留 GHCR 发行清单及备份。
2. 扩展发行清单和允许的镜像引用校验，绑定实际仓库，支持认证拉取与回滚；不只替换一个域名字符串。
3. 如使用支持 VPC 接入的 TCR，配置服务器所在 VPC 的内网访问及域名解析。同地域不等于自动走内网。
4. 在该服务器实测完整镜像拉取、迁移演练和恢复后，再选择它作为测试环境下载源。
5. 给新仓库接入相同的保留策略：最近 5 个普通版本，额外保护当前部署、指定回滚及固定保留版本。GHCR 原有清理启用条件维持不变，未验证两个环境状态时不能放开清理。

## 本次验证（2026-09-10）

- 当前代码的后端 Maven 构建通过（跳过业务测试执行）；114 项隔离 Linux CD 单元测试及 Actions 语法检查通过。
- 对刚构建的实际 JAR 执行 Boot tools 分层，690 个依赖 JAR 内容一致、49 个版本迁移文件通过哈希校验，Java 类路径探针通过。
- 分层文件未压缩大小：稳定依赖 443,537,602 字节，应用及本项目模块 376,717,602 字节。首次下载仍较大，不应承诺每次只下载几 MB。
- 使用刚构建 JAR 和实际 Dockerfile 运行阶段在本机构建探针镜像，以无网络、只读、非 root 容器验证类路径；从停止的探针容器复制迁移运行时并验证到 V049。没有启动 ERP 应用或连接数据库，探针容器和镜像标签随后删除。
- 正式镜像发布、新镜像的服务器完整下载及首次 CD 数据库演练，仍需推送后由 GitHub CI/CD 验证。本次未进行服务器切换。
