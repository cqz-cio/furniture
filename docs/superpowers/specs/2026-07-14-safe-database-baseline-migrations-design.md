# Oakved 安全数据库基线与迁移设计

## 目标

建立一套不会在日常启动时覆盖数据库的部署机制：空环境首次部署只需导入一份完整的 `oakved-baseline.sql`，后续升级只执行尚未运行的编号迁移。数据库重建从日常启动中移除，改为需要备份和明确人工确认的独立操作。

## 当前问题

- `start-local-infra.ps1 -Recreate` 会执行 `docker compose down -v`，直接删除 MySQL 和 Redis 数据卷。
- 本地启动脚本会重复执行若干 SQL 文件，但没有统一的版本、校验和或执行记录。
- Docker 首次初始化挂载多个 SQL 文件，部署者无法通过一个完整 SQL 重建相同环境。
- 商城的 26 条家具商品由独立 PowerShell/Java 程序写入，不属于可审计的数据库基线。
- ERP 结构和商城—ERP 映射是后加迁移；当前数据库缺少这些表时，管理页面会出现 ERP 接口错误。

## 选定方案

采用“编号迁移为事实来源、自动生成单文件基线”的方案。

不引入 Flyway 或 Liquibase。现有 PowerShell、MySQL 8.0 和 Node/Vitest 足以提供生成、执行与验证能力，避免给 Java 服务增加新的运行依赖。

## 文件与职责

### 编号迁移目录

在 `yudao-cloud/sql/mysql/migrations/` 中维护按版本排序的 SQL：

- 已发布迁移只读，不允许原地修改。
- 新变更只能新增更高版本文件。
- 文件名使用 `VNNN__description.sql`。
- 每个文件必须可在 MySQL 8.0 上独立执行，失败时不得写入迁移记录。

首批迁移覆盖现有项目所需的模块扩展，包括会员、交易、礼物清单、商品详情、收藏、ERP 集成、统计看板及相关结构。

### 完整首次部署脚本

生成并提交 `yudao-cloud/sql/mysql/oakved-baseline.sql`。生成顺序固定为：

1. 基础 `ruoyi-vue-pro.sql`；
2. Quartz 和项目模块基础表；
3. 全部编号迁移；
4. 租户 `121` 的可登录基础数据；
5. 26 条家具 SPU、对应 SKU、分类、品牌；
6. 对应 ERP 商品、仓库、库存和商城—ERP 映射；
7. `schema_migrations` 中与本次基线内容一致的迁移记录。

基线不包含真实会员、订单、支付、访问日志或其他运行期业务数据。它只包含启动系统和验收完整功能所需的基础数据与演示商品。

基线生成器每次从受版本控制的源 SQL 重新生成文件，不允许手工编辑生成结果。相同提交重复生成必须得到相同字节内容。

### 迁移记录

数据库增加 `schema_migrations` 表，至少包含：

- `version`：唯一迁移版本；
- `description`：迁移说明；
- `script_name`：文件名；
- `checksum_sha256`：文件 SHA-256；
- `installed_at`：执行完成时间。

迁移执行器按版本升序运行，并使用 MySQL advisory lock 防止两个启动进程同时迁移。

已记录版本的文件校验和不一致时必须停止，提示迁移被修改；不得自动覆盖数据库里的历史记录。只有 SQL 成功执行后才能插入迁移记录。

### 日常启动

`start-local-infra.ps1` 的职责调整为：

1. 执行 `docker compose up -d`；
2. 等待 MySQL 健康；
3. 执行安全迁移器；
4. 输出数据库、已执行版本和本次新增版本。

日常启动脚本不再提供 `-Recreate`，也不执行 `down -v`。Docker Compose 首次创建空卷时只挂载完整 `oakved-baseline.sql`，不再并行挂载一组顺序敏感的初始化 SQL。

### 独立重建

新增单独的本地重建脚本。执行顺序固定为：

1. 确认 MySQL 容器可访问；
2. 使用 `mysqldump --single-transaction --routines --triggers` 生成带时间戳备份；
3. 验证备份文件存在、非空并包含数据库结构；
4. 要求交互输入完整文本 `RESET OAKVED LOCAL DATA`；
5. 仅在匹配后执行 `docker compose down -v`；
6. 重新启动并由完整基线初始化；
7. 执行结构和演示数据验收。

非交互环境默认拒绝重建。自动化如确有需要，必须同时显式传入确认值和备份目录；不能通过普通启动参数间接触发。

## 现有数据库升级

现有非空数据库不重新导入基线。迁移器创建 `schema_migrations` 后按顺序处理编号迁移：

- 对尚未具备目标结构的迁移执行 SQL 并记录；
- 对已经具备完整目标结构、但缺少历史记录的迁移，通过迁移自带的验证查询确认后补记记录；
- 结构只完成一部分时停止并报告缺失项，不猜测、不删除数据，也不自动标记成功。

当前 26 条商品必须保留。ERP 迁移完成后，以稳定业务键为依据补齐 26 条 ERP 商品与映射；重复执行不得生成重复商品、库存或映射。

## 数据安全规则

- 启动、构建、测试和迁移命令不得删除 Docker volume。
- 基线仅允许导入空数据库；发现业务表已有数据时必须拒绝。
- 任何破坏性操作前必须先完成可验证备份。
- 迁移脚本不得物理删除现有商城商品、ERP 商品、会员、订单或支付记录。
- 数据修复必须使用独立、可审查的编号迁移，不能隐藏在启动脚本中。
- 密码等本地演示凭据保持现有开发约定；生产部署必须通过环境变量提供，不写入新的生产基线秘密。

## 验证与验收

### 静态自动化测试

扩展现有 Vitest 数据库迁移检查，验证：

- 日常启动脚本不包含 `down -v` 或 `-Recreate`；
- 重建脚本包含备份、备份校验和精确确认文本；
- 编号迁移严格递增且文件名唯一；
- 基线生成结果与已提交文件一致；
- 基线包含 `schema_migrations`、商城、ERP 和映射结构；
- 基线包含租户 `121` 的 26 条 SPU/SKU 和对应 ERP 数据；
- Docker Compose 只挂载完整基线作为首次初始化入口。

### 空库验收

在临时 MySQL 8.0 数据卷导入基线，验证：

- 所有结构创建成功；
- 迁移记录与迁移目录一致；
- 租户 `121` 有且仅有 26 条有效演示 SPU 和 26 条 SKU；
- 26 条 ERP 商品均有库存和商城映射；
- 关键唯一键、外键语义和租户边界通过审计。

### 升级与幂等验收

- 对当前数据库执行迁移时不改变已有 26 条商城商品主键；
- 连续运行迁移器两次，第二次执行零条迁移；
- 人为修改一个已记录迁移文件后，迁移器因校验和不一致退出；
- 人为制造部分 ERP 结构后，迁移器停止并说明冲突；
- 普通启动连续运行两次，数据库卷和业务数据保持不变。

### 重建验收

- 确认文本错误或缺失时不删除数据卷；
- 备份失败或备份为空时不删除数据卷；
- 完整确认后可以从空卷恢复到基线状态；
- 重建前备份可由单独恢复流程重新导入。

## 不在本次范围

- 无来源地复原已经丢失的原始 100 多条 ERP 商品。
- 将真实生产订单、会员、支付和访问日志写入演示基线。
- 自动执行生产数据库重建。
- 引入 Flyway、Liquibase 或新的数据库迁移服务。

## 完成标准

首次部署者可用一份 `oakved-baseline.sql` 创建可登录、可查看 26 条商城商品并具备对应 ERP 库存映射的完整本地数据库。日常启动和后续升级不会删除数据卷；所有数据库变化都有版本、校验和、执行记录和自动化验证；清空重建只能通过独立、先备份并明确确认的流程完成。
