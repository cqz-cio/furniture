# 支付流程与安全边界梳理

本文只梳理支付环节，不包含地址核验闭环。地址环节的结束点是“订单已使用用户确认后的收货信息创建成功”。支付环节从“订单创建成功，需要收款”开始。

## 1. 支付环节的核心目标

支付环节要解决三件事：

1. 确认这笔订单是否需要付款。
2. 如果需要付款，安全地创建支付单并跳转/提交到支付渠道。
3. 支付渠道返回结果后，准确、安全、不可重复地更新订单状态。

一句话理解：支付环节不是“点一下按钮跳支付页”，而是“订单金额、支付单、渠道返回、后端回调、订单状态”必须全部对得上。

## 2. 支付流程总览

```text
订单创建成功
  -> 判断订单金额
    -> 0 元订单：直接标记为无需支付，进入订单完成/待发货
    -> 大于 0：创建或提交支付单
      -> 前端提交支付请求
      -> 后端校验订单和金额
      -> 后端生成支付参数
      -> 前端跳转/展示支付渠道
      -> 用户完成/取消/失败支付
      -> 支付渠道回调后端
      -> 后端验签、验金额、验订单归属、验状态
      -> 更新订单支付状态
      -> 前端订单页拉取最新状态展示
```

## 3. 前端负责的边界

前端主要负责“流程控制”和“用户体验”，不能把前端返回当作最终支付成功依据。

前端应该做：

1. 订单创建成功后再进入支付。
2. 付款金额大于 0 才展示支付动作。
3. 支付通道为空、配置异常、支付单 id 缺失时阻止提交。
4. 防止用户重复点击导致重复提交。
5. 支付返回后，根据订单详情接口重新拉取真实状态。
6. 如果支付失败、取消、未知，允许用户回到订单继续支付。
7. 如果订单已经支付，不能再次提交支付。

前端不能做：

1. 不能只因为跳转回来带了 `success` 就把订单当作已支付。
2. 不能自己修改订单支付状态。
3. 不能相信浏览器里传回来的金额、订单号、支付状态。
4. 不能让无效支付渠道继续提交。

## 4. 后端负责的边界

后端是支付安全的核心，所有最终状态必须以后端校验为准。

后端应该做：

1. 校验当前用户是否有权支付这笔订单。
2. 校验订单是否存在、是否属于当前用户、是否还需要支付。
3. 校验支付金额必须等于订单应付金额。
4. 校验支付渠道是否合法、是否启用。
5. 创建支付单时记录订单号、支付单号、金额、渠道、状态。
6. 接收支付渠道回调时验签。
7. 回调里再次校验订单号、金额、支付单状态。
8. 支付成功后用事务更新订单和支付单状态。
9. 对重复回调做幂等处理。
10. 对异常回调记录日志，不能静默吞掉。

后端不能做：

1. 不能因为前端说支付成功就直接改订单为已支付。
2. 不能允许订单金额和支付金额不一致。
3. 不能允许已支付订单再次生成新的有效支付。
4. 不能允许无用户归属校验的支付提交。
5. 不能把第三方回调失败当作成功处理。

## 5. 数据库负责的边界

数据库是最终账本，支付状态最终必须落到数据库里。

数据库里至少需要保存：

1. 订单 id。
2. 订单号。
3. 用户 id。
4. 应付金额。
5. 支付状态。
6. 支付单 id。
7. 支付渠道。
8. 支付成功时间。
9. 回调流水或渠道交易号。
10. 状态更新时间。

关键原则：

1. 订单状态和支付单状态必须一致。
2. 支付成功更新要放在事务里。
3. 同一个支付渠道交易号不能重复入账。
4. 金额字段不能只依赖前端传入。
5. 订单创建金额和支付回调金额必须能追溯。

## 6. Redis / 缓存可能参与的边界

Redis 不应该作为支付最终账本，它只能做临时状态和防护。

Redis 常见用途：

1. 用户登录态或 token 缓存。
2. 支付提交防重复点击。
3. 支付单短期锁。
4. 回调幂等锁。
5. 订单详情短期缓存。
6. 风控限流。

注意边界：

1. Redis 里显示成功不代表支付最终成功。
2. Redis 只能辅助防重复，最终必须看数据库。
3. Redis 锁失效后，数据库幂等仍然必须存在。
4. 支付回调不能只靠缓存判断是否处理过。

## 7. 支付渠道负责的边界

支付渠道负责真实收款、返回支付结果、回调通知。

支付渠道应该提供：

1. 支付页面或支付参数。
2. 渠道支付单号。
3. 支付成功/失败/取消状态。
4. 后端异步回调。
5. 回调签名。
6. 可查询支付结果的接口。

我们系统不能完全信任：

1. 前端跳转返回参数。
2. 用户浏览器里的支付状态。
3. 没有验签的回调。
4. 金额不一致的成功通知。
5. 订单号不匹配的成功通知。

### 7.1 海外信用卡渠道的额外边界

如果最后接入 Stripe、Adyen、Braintree 等海外信用卡支付渠道，仍然遵守同一条主链路：前端发起支付，后端创建渠道支付会话或支付意图，渠道收款后通过可信回调更新支付单和订单状态。

为了降低安全和合规风险，优先采用渠道托管支付页，例如 Stripe Checkout。前端拿到的应该是支付跳转地址或渠道 SDK 所需的临时参数，而不是完整信用卡信息。

必须做到：

1. 当前 checkout 页面里的信用卡输入框只能作为占位体验，不能直接用于真实收款。
2. 真实卡号、CVV、磁道信息不能进入我们的前端状态、后端接口、日志或数据库。
3. 如果使用 Stripe Elements 等嵌入式方案，卡号输入必须由渠道 SDK 托管，后端只接收 `paymentMethod`、`clientSecret`、`paymentIntent`、`checkoutSession` 等渠道引用。
4. 后端密钥、webhook secret、商户私钥只能放在后端运行环境变量或安全配置中心，不能写入前端仓库。
5. 前端最多暴露渠道允许公开的 publishable key。
6. 数据库最多保存卡品牌、尾号 last4、渠道交易号、金额、币种、支付状态、支付时间等非敏感账务信息。
7. 回调必须验签，并校验事件 id、渠道交易号、金额、币种、订单号、支付单 id 和订单归属。
8. 同一个 webhook event id 或渠道交易号不能重复入账。

推荐的 Stripe Checkout 形态：

```text
订单创建成功
  -> Yudao 创建 payOrderId
  -> 前端调用 /app-api/pay/order/submit
  -> 后端根据 Stripe 渠道创建 Checkout Session
  -> 前端跳转 Stripe 托管支付页
  -> 用户在 Stripe 页面输入信用卡并完成 3DS 等验证
  -> Stripe webhook 回调后端
  -> 后端验签、验金额、验币种、验订单
  -> 后端幂等更新支付单和业务订单
  -> 前端订单页重新拉取真实状态
```

不推荐第一版直接做自建信用卡表单。除非后续明确需要内嵌体验，否则托管支付页更容易控制 PCI 合规范围，也更容易把支付安全边界保持在后端和渠道之间。

## 8. 必须判断的边界情况

### 8.1 订单金额为 0

判断：

- 应付金额等于 0。

处理：

- 不创建第三方支付。
- 后端直接标记为无需支付或已支付。
- 进入订单完成/待发货流程。

风险：

- 不能让前端自己决定 0 元订单是否成功。
- 后端必须确认最终金额确实为 0。

### 8.2 支付通道未配置

判断：

- 支付通道为空。
- 支付通道是占位值。
- 支付通道在后端未启用。

处理：

- 前端不允许提交。
- 后端拒绝支付创建。
- 给出可理解的错误提示。

风险：

- 不能生成无效支付单。
- 不能让订单卡在“待支付但不可支付”的状态里没人知道。

### 8.3 支付单 id 无效

判断：

- 支付单 id 为空。
- 支付单 id 不是数字。
- 支付单 id 和订单不匹配。

处理：

- 前端阻止继续支付。
- 后端拒绝提交。
- 订单页允许重新拉取真实订单状态。

风险：

- 防止用户篡改 id 支付别人的订单。

### 8.4 用户重复点击支付

判断：

- 同一订单短时间多次提交。
- 同一支付单重复提交。

处理：

- 前端按钮 loading / disabled。
- Redis 可做短期防重复锁。
- 后端以数据库状态做最终幂等判断。

风险：

- 不能重复扣款。
- 不能重复生成有效支付单。

### 8.5 已支付订单再次支付

判断：

- 订单状态已经是已支付。
- 支付单状态已经成功。

处理：

- 前端不展示继续支付。
- 后端拒绝新的支付提交。
- 订单页展示已支付状态。

风险：

- 防止重复收款。

### 8.6 支付失败

判断：

- 渠道返回失败。
- 后端查询结果失败。
- 回调明确失败。

处理：

- 订单保持待支付或支付失败。
- 允许用户重新支付。
- 记录失败原因。

风险：

- 失败不能误判为成功。
- 重试不能绕过金额和订单校验。

### 8.7 用户取消支付

判断：

- 用户关闭支付页。
- 渠道返回取消。
- 前端没有收到明确成功。

处理：

- 订单保持待支付。
- 订单页显示继续支付。

风险：

- 取消不等于失败，也不等于成功。

### 8.8 支付返回状态未知

判断：

- 前端返回参数缺失。
- 回调延迟。
- 前端看到状态与后端状态不一致。

处理：

- 前端提示等待确认。
- 前端重新拉取订单详情。
- 后端以渠道回调或主动查询结果为准。

风险：

- 不能因为前端未知就改状态。
- 不能因为回调慢就重复扣款。

### 8.9 支付回调重复到达

判断：

- 同一个渠道交易号多次回调。
- 同一个支付单多次成功通知。

处理：

- 后端验签。
- 后端检查支付单状态。
- 如果已经成功，直接返回成功给渠道，但不重复改账。

风险：

- 避免重复入账。

### 8.10 回调金额不一致

判断：

- 渠道回调金额 != 订单应付金额。

处理：

- 拒绝更新为已支付。
- 记录安全日志。
- 后台人工介入。

风险：

- 这是高风险情况，不能自动放行。

### 8.11 回调订单不匹配

判断：

- 渠道回调中的订单号、支付单号、用户归属无法匹配。

处理：

- 拒绝处理。
- 记录日志。
- 必要时报警。

风险：

- 防止错单、串单、恶意伪造。

### 8.12 支付成功但订单更新失败

判断：

- 渠道已成功。
- 数据库事务失败或网络异常。

处理：

- 记录回调原文。
- 允许后端补偿任务重新处理。
- 前端显示等待确认或支付处理中。

风险：

- 用户已经付钱，不能丢单。
- 不能只依赖前端页面状态。

### 8.13 订单已取消后收到支付成功

判断：

- 订单状态已取消。
- 后续收到成功回调。

处理：

- 不直接改成已支付。
- 进入异常订单处理。
- 根据业务规则退款或人工确认。

风险：

- 防止取消订单被意外发货。

## 9. 安全判断优先级

支付安全判断建议按这个顺序：

1. 用户身份是否合法。
2. 订单是否存在。
3. 订单是否属于当前用户。
4. 订单是否需要支付。
5. 支付通道是否可用。
6. 支付单是否有效。
7. 金额是否一致。
8. 支付状态是否可变更。
9. 回调是否验签通过。
10. 是否重复处理。

任何一步不通过，都不能把订单改为已支付。

## 10. 当前已经覆盖的方向

当前代码已经围绕以下方向做了支付闭环设计：

1. 空支付通道/占位支付通道拦截。
2. 无效支付单 id 拦截。
3. 0 元订单单独分支。
4. 已支付订单避免重复支付。
5. 支付失败/取消/未知状态恢复。
6. 订单页继续支付能力。
7. 后端支付回调参数校验。
8. 后端订单金额、归属、状态一致性校验。
9. 支付回调幂等处理。

## 11. 上线前还需要重点确认

上线前建议重点确认这些外部条件：

1. 真实支付通道已经配置完成。
2. 支付通道支持测试环境或沙盒环境。
3. 后端回调地址公网可访问。
4. 回调验签配置正确。
5. 支付金额单位一致，比如分/元不能混。
6. 支付成功后订单状态能正确变更。
7. 重复回调不会重复入账。
8. 支付失败和取消能回到订单页继续支付。
9. 异常订单有后台人工处理入口。
10. 支付日志里能查到订单号、支付单号、渠道交易号。
11. 如果接海外信用卡，确认真实卡数据不经过我们自己的接口、日志和数据库。
12. 如果接 Stripe 等 webhook 渠道，确认 webhook secret、事件验签、事件幂等和币种校验已经跑通。

## 12. 最简单的业务结论

支付环节要记住一句话：

前端只能负责“引导用户去支付”，真正判断是否付款成功必须以后端收到并校验过的支付渠道结果为准。

只要做到“订单金额一致、订单归属一致、支付单一致、渠道回调可信、状态更新幂等”，支付安全边界就基本站稳了。
