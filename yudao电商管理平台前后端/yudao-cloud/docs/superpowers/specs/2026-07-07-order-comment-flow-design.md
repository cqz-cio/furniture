# 订单后评价一期设计文档

**日期**: 2026-07-07

**范围定位**: 一期仅覆盖 `yudao-cloud` 后端能力扩展与商城前端对接方案，不包含商家后台审核/回复联动的实现落地。

**仓库前提**:
- 当前工作区内存在交易、商品评论相关后端代码。
- 当前工作区内未发现商城前端完整源码，前端部分先输出页面、交互、接口对接和验收方案，供后续前端仓库实施时使用。

---

## 1. 背景与目标

当前订单链路已经具备基础评价能力：
- 交易模块已有订单、订单项 `commentStatus` 字段。
- 订单侧已有待评价数量统计 `uncommentedCount`。
- 订单侧已有单个订单项评价接口与超时自动评价任务。
- 商品侧已有评论落库、评论分页、评论显隐与回复能力。

但用户侧仍缺少完整的“订单完成后集中评价”体验，当前更接近后端半成品状态，尚未形成面向顾客的完整闭环。

本期目标是建立一个完整的用户评价闭环：
1. 用户可从订单列表、订单详情进入整单集中评价页。
2. 用户在一个页面内完成整单下全部待评价商品的评价。
3. 前端通过新的整单批量评价接口一次提交整单评价。
4. 后端以整单为原子单位完成校验、评论创建、状态更新和日志记录。
5. 成功后订单从“待评价”切换为“已评价”，待评价数量同步刷新。

---

## 2. 一期范围

### 2.1 包含内容

- 新增整单集中评价产品形态。
- 新增整单批量评价接口。
- 复用现有商品评论落库能力。
- 更新订单侧状态汇总逻辑，保证整单完成后一次性变更为已评价。
- 输出商城前端页面结构、字段约束、错误处理、提交流程与验收标准。

### 2.2 不包含内容

- 商家后台评论审核、回复、可见性运营联动。
- 评论敏感词、审核流、风控增强。
- 评价晒图运营玩法、评价奖励、评价返积分。
- 已评价内容的前台“追评”“修改评价”“删除评价”。

## 3. 现状分析

### 3.1 已有后端能力

现有后端已经具备以下基础设施：
- `AppTradeOrderController` 已有单订单项评价接口 `/trade/order/item/create-comment`。
- `TradeOrderUpdateServiceImpl` 已有 `createOrderItemCommentByMember` 与 `createOrderItemCommentBySystem`。
- `ProductCommentServiceImpl` 已有评论创建能力。
- `TradeOrderAutoCommentJob` 已有超时自动评价任务。
- 订单列表、订单详情返回结构中已有 `commentStatus`。

### 3.2 现有问题

- 现有接口语义是“按订单项提交”，不适合支撑整单集中评价页面。
- 前端若循环调用旧接口，会带来部分成功、部分失败的状态复杂度。
- 若没有整单原子提交，用户看到的是“一次提交”，系统却可能落成“半单已评价”，产品语义不一致。
- 当前工作区未包含商城前端完整源码，前端落地需依据本设计文档在实际前端仓库补齐。

## 4. 产品方案选择

本期最终选择：

**整单集中评价页 + 新增批量评价接口**

### 4.1 选择原因

- 与用户心智一致。用户进入的是“订单评价页”，提交时理应对应“整单完成评价”。
- 能避免前端逐条提交带来的部分成功状态。
- 后端通过单事务控制整单一致性，便于排查和统计。
- 后续可继续复用商品评论表与后台评论管理能力，不会推翻现有结构。

### 4.2 放弃方案

#### 方案 A: 整单页面 + 前端循环调用旧接口

优点:
- 后端改动小。

缺点:
- 前端实现复杂。
- 容易出现部分提交成功。
- 用户点击一次提交，却可能得到半成功结果，体验和数据状态都不稳定。

#### 方案 B: 逐商品单独评价

优点:
- 最容易实现。

缺点:
- 需要用户重复进入多个评价页。
- 不符合本次选定的“整单集中评价”产品方向。

## 5. 核心产品规则

### 5.1 评价入口规则

订单满足以下条件时展示 `去评价`：
- `status = COMPLETED`
- `commentStatus = false`

入口位置：
- 我的订单列表页
- 订单详情页

### 5.2 页面填写规则

整单评价页一次展示该订单下全部待评价商品。

每个商品卡片包含：
- 商品图片
- 商品名称
- SKU/规格信息
- 星级评分
- 文字评价
- 图片上传

字段约束：
- 星级评分必填
- 文字评价选填
- 图片选填
- 匿名状态按整单维度控制，一次提交统一生效

### 5.3 提交规则

本期采用“整单一次提交，整单原子成功或失败”的规则：
- 页面内所有待评价商品都必须完成必填项后才允许提交。
- 提交时调用新的整单批量评价接口，而不是逐商品循环调用旧接口。
- 后端任一商品评价创建失败，整单回滚。

### 5.4 用户体验降门槛规则

为了避免“整单评价”给用户造成过重负担，本期同时采用以下降门槛措施：
- 星级必填，文字和图片不强制。
- 页面提供 `全部默认 5 星` 快捷操作。
- 提交失败后保留用户已填内容，不要求重新填写。

## 6. 交互流程设计

### 6.1 主流程

1. 用户在订单列表页或订单详情页点击 `去评价`。
2. 前端进入整单评价页，请求订单下全部待评价商品。
3. 页面渲染所有商品卡片，用户完成评分，可选填写文字和图片。
4. 用户点击 `提交评价`。
5. 前端先做本地校验，只检查每个商品是否已完成星级。
6. 校验通过后，请求整单批量评价接口。
7. 后端整单完成校验、评论创建、状态更新。
8. 成功后前端返回订单详情并刷新列表计数。

### 6.2 失败流程

提交失败时统一采用固定提示文案：

`网络异常，请稍后重试`

失败后的前端行为：
- 停留在当前整单评价页
- 保留已填写的星级、文字、图片、匿名状态
- 允许用户直接再次点击提交
- 提交按钮在请求期间进入 `loading`，避免重复提交

### 6.3 本地校验流程

前端本地校验不使用“网络异常”文案。

仅在以下场景进行本地拦截：
- 某个商品未选择星级

本地校验失败时：
- 不发起请求
- 页面内直接提示用户补齐未完成项

## 7. 后端设计

### 7.1 保留与新增接口策略

保留现有接口：
- `POST /trade/order/item/create-comment`

新增接口：
- `POST /trade/order/create-comments`

设计原则：
- 旧接口继续保留，兼容已有能力或后续其他入口。
- 新接口仅服务整单集中评价场景。
- 一期不删除旧接口，不合并两个入口语义。

### 7.2 新接口定义

#### 请求路径

`POST /trade/order/create-comments`

#### 请求体示例

```json
{
  "orderId": 10001,
  "anonymous": false,
  "items": [
    {
      "orderItemId": 20001,
      "descriptionScores": 5,
      "benefitScores": 5,
      "content": "做工很好，颜色也对版",
      "picUrls": [
        "https://cdn.example.com/comment/1.jpg"
      ]
    },
    {
      "orderItemId": 20002,
      "descriptionScores": 4,
      "benefitScores": 5,
      "content": "",
      "picUrls": []
    }
  ]
}
```

#### 返回体示例

```json
{
  "code": 0,
  "data": {
    "orderId": 10001,
    "commentedItemCount": 2,
    "commentIds": [30001, 30002]
  }
}
```

### 7.3 新增 VO 建议

建议新增：
- `AppTradeOrderCommentCreateReqVO`
- `AppTradeOrderCommentCreateReqVO.Item`
- `AppTradeOrderCommentCreateRespVO`

字段建议如下：

#### AppTradeOrderCommentCreateReqVO

- `Long orderId`
- `Boolean anonymous`
- `List<Item> items`

#### AppTradeOrderCommentCreateReqVO.Item

- `Long orderItemId`
- `Integer descriptionScores`
- `Integer benefitScores`
- `String content`
- `List<String> picUrls`

#### AppTradeOrderCommentCreateRespVO

- `Long orderId`
- `Integer commentedItemCount`
- `List<Long> commentIds`

### 7.4 服务层设计

建议新增服务方法：

`createOrderCommentsByMember(Long userId, AppTradeOrderCommentCreateReqVO reqVO)`

建议在 `TradeOrderUpdateService` 与 `TradeOrderUpdateServiceImpl` 中增加整单评价方法，内部复用已有单订单项评论创建能力，但由整单方法统一控制事务和状态更新。

### 7.5 后端处理顺序

后端处理顺序建议固定为：

1. 校验订单存在且属于当前用户
2. 校验订单状态为 `COMPLETED`
3. 校验订单 `commentStatus = false`
4. 查询该订单下全部未评价订单项
5. 校验请求中的 `orderItemId` 集合与待评价订单项集合一致
6. 逐项转换为商品评论创建 DTO
7. 创建所有评论记录
8. 批量更新订单项 `commentStatus = true`
9. 更新订单 `commentStatus = true`
10. 更新订单完成时间或评价完成时间字段
11. 写入订单日志
12. 返回评论结果集合

### 7.6 事务策略

整单批量评价必须使用单事务。

约束规则：
- 任一评论创建失败，整单事务回滚
- 任一状态更新失败，整单事务回滚
- 不允许数据库层保留半单评价状态

## 8. 前端对接方案

> 当前仓库缺少商城前端完整源码，以下为前端仓库实施时的页面与接口对接设计。

### 8.1 页面新增建议

建议新增页面：
- 订单评价页 `order-comment`

页面职责：
- 拉取订单下全部待评价商品
- 承载整单填写体验
- 负责前端本地校验
- 调用整单批量评价接口

### 8.2 页面数据结构建议

页面本地状态建议包含：
- `orderId`
- `anonymous`
- `items[]`
- `submitting`
- `loaded`

单商品本地状态建议包含：
- `orderItemId`
- `spuName`
- `picUrl`
- `properties`
- `descriptionScores`
- `benefitScores`
- `content`
- `picUrls`

### 8.3 页面交互细节

建议交互规则：
- 进入页面后默认全部星级为空，不直接默认提交
- 提供 `全部默认 5 星` 按钮，减少用户操作成本
- 用户可手动改单个商品评分
- 文字框支持空内容提交
- 图片最多沿用后端单商品评论的现有限制

### 8.4 提交前校验

前端提交前只做轻量校验：
- 每个商品必须完成 `descriptionScores`
- 每个商品必须完成 `benefitScores`

若业务上最终只保留一个星级字段，则页面和接口可以同步简化，但在当前后端结构下，建议继续沿用双评分字段，避免额外改动评论模型。

### 8.5 提交成功后的页面行为

提交成功后：
- toast 成功提示
- 返回订单详情页
- 刷新订单详情数据
- 刷新订单列表数据
- 刷新待评价数量 `uncommentedCount`

### 8.6 提交失败后的页面行为

提交失败后：
- toast 文案统一为 `网络异常，请稍后重试`
- 页面不返回
- 页面内容不清空
- `submitting` 状态恢复为可点击

## 9. 异常与容错策略

### 9.1 后端业务异常

后端内部仍需要区分业务异常类型，以便日志、排查和后续监控使用，例如：
- 订单不存在
- 订单不属于当前用户
- 订单未完成
- 订单已评价
- 订单项不属于该订单
- 订单项已评价
- 请求项集合不完整

### 9.2 前端展示策略

虽然服务端内部区分业务异常，但本期前端统一外显为：

`网络异常，请稍后重试`

这样做的原因：
- 减少用户面向异常分支的认知负担
- 避免暴露复杂业务状态差异
- 保持一期实现简单

### 9.3 日志与排查

由于前端提示统一，后端必须增强日志：
- 记录订单 ID
- 记录用户 ID
- 记录请求订单项 ID 列表
- 记录失败原因
- 记录事务回滚上下文

否则前台错误提示收口后，后端排障成本会显著上升。

## 10. 与现有能力的关系

### 10.1 与单订单项评价接口的关系

- 保留旧接口
- 新增整单接口
- 整单接口内部可复用已有评论 DTO 转换与评论落库逻辑
- 后续若确认所有前端流量都迁移完毕，再评估是否逐步弱化旧入口

### 10.2 与自动默认评价任务的关系

现有自动默认评价任务继续保留，且不应被本期设计破坏。

要求：
- 人工整单评价成功后，不再被自动评价任务重复处理
- 自动评价任务仍以未评价订单为目标集
- 新增整单评价接口后，订单 `commentStatus` 和订单项 `commentStatus` 仍是自动任务筛选依据

### 10.3 与待评价统计的关系

现有 `uncommentedCount` 继续复用，不单独新增统计口径。

成功标准：
- 整单评价提交成功后，该订单不再计入待评价数量
- 用户返回订单列表时待评价 tab 或数量可见地同步变化

## 11. 验收标准

### 11.1 功能验收

1. 已完成且未评价订单，在订单列表页与详情页均可进入评价页
2. 评价页一次展示该订单下全部待评价商品
3. 每个商品至少完成评分后方可提交
4. 前端通过一个整单批量接口完成提交
5. 提交成功后所有订单项 `commentStatus` 变为 `true`
6. 提交成功后订单 `commentStatus` 变为 `true`
7. 提交成功后订单从“待评价”集合中移除
8. 待评价数量同步减少

### 11.2 一致性验收

1. 任一评论创建失败时整单回滚
2. 不出现同一订单下部分商品已评价、部分未评价的半成功状态
3. 重复提交不会生成重复评论
4. 跨订单伪造 `orderItemId` 不可提交成功

### 11.3 体验验收

1. 提交失败统一提示 `网络异常，请稍后重试`
2. 提交失败后用户已填写内容保留
3. 用户可直接重试，不需要重新进入页面
4. 提交期间按钮可防重

## 14. 风险与后续建议

### 14.1 一期风险

- 当前商城前端源码不在此仓库，前端实施需要跨仓库协同。
- 前端统一使用“网络异常，请稍后重试”会降低用户获得具体原因的能力，需依赖后端日志排查。
- 若未来产品要求允许部分商品单独评价，本期整单原子提交规则需要调整。

### 14.2 后续二期可扩展方向

- 商家回复与前台展示联动
- 评论审核/显隐运营流
- 评价奖励、返积分、优惠券激励
- 追评能力
- 更细的失败码与监控埋点

## 15. 结论

本期建议以“整单集中评价页 + 整单批量评价接口”为主方案落地，并明确以下原则：
- 用户体验上是整单集中填写
- 数据语义上是整单一次提交
- 一致性上是整单原子成功或失败
- 用户门槛上只强制评分，不强制长文和图片
- 失败提示统一为 `网络异常，请稍后重试`

这套方案在不推翻现有后端评论体系的前提下，能最快补齐用户评价闭环，并为下一阶段的运营和后台联动留下清晰扩展点。
